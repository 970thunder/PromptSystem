# PromptOS 开发与交付规范

## 目标

保证每次功能修改都可以被复现、验证、追溯和回滚。代码、测试、文档和部署配置属于同一个交付单元，不以“能编译”替代功能验收。

## 开始修改前

1. 阅读 `AGENTS.md`、`TODO.md` 以及与任务相关的 API 契约和部署文档。
2. 执行 `git status --short --branch`，确认当前分支和已有改动；不得覆盖他人未提交的修改。
3. 从 `origin` 获取最新信息。默认在当前开发分支工作，不直接改动生产分支历史。
4. 明确本次变更范围、验收条件和需要补充的测试；数据库变更必须新增 `sql/migrations/*.sql`。

## 编码约定

- 前端沿用 Vue 3、TypeScript、Pinia、Naive UI、Tailwind 和现有设计 token；组件应提供加载、成功、失败、空数据、禁用和移动端状态。
- 后端沿用 `handler -> service -> store` 边界；权限、校验和事务逻辑不得复制到多个 handler。
- 所有接口遵循统一响应结构和稳定 `errorCode`；不得把 SQL、密钥或内部错误详情返回给用户。
- 新功能至少补一条单元、组件、集成或端到端测试；风险较高的认证、上传、权限、互动功能必须补充失败路径测试。
- 不提交 `.env`、密钥、真实上传文件、构建产物、日志、测试报告和本地 IDE 文件。

## 测试门禁

### 前端变更

```powershell
cd src/frontend
npm install
npm run lint:check
npm test
npm run build
npm run contract:check
```

涉及页面、路由或交互时，追加 `npm run test:e2e`，并用桌面 `1440x900` 和移动 `390x844` 视口检查无白屏、控制台异常和横向溢出。

### 后端变更

```powershell
cd src/backend
gofmt -l .
go vet ./...
go test ./...
```

涉及 MySQL、Redis、对象存储、SMTP 或 Docker 时，必须追加对应的真实依赖验证；如果依赖不可用，要记录阻断原因和未验证范围，不得把 mock 结果描述为生产链路通过。

### 联调变更

验证健康检查、鉴权、核心读写流程、错误响应、权限边界和数据持久化。上传功能至少覆盖合法文件、伪造 MIME、超限、归属校验、失败重试和资源访问；互动功能至少覆盖幂等、取消和未登录拒绝。

## 提交与推送 SOP

每个可独立交付的功能按以下顺序执行：

1. 完成功能代码、测试、文档和必要的迁移。
2. 运行本节测试门禁，并记录实际命令和结果。
3. 执行 `git diff --check`，确认 `git status` 中没有禁止提交的文件。
4. 使用 Conventional Commits 提交，例如 `feat(publish): add draft validation` 或 `fix(auth): silence anonymous session probe`。
5. 提交成功后立即执行 `git push origin <当前分支>`，不得长期积压已通过测试的本地提交。
6. 推送后执行 `git status --short --branch` 和 `git log -1 --oneline`，确认工作树干净且远端已更新。
7. 在任务记录或交付说明中写明提交号、推送分支、测试结果和未完成的外部依赖。

测试失败时：修复后重新执行完整门禁；不能修复时保留失败输出，不提交为“完成”。外部服务不可用时可以提交不依赖该服务的代码，但必须明确标注验证边界，并在外部依赖恢复后补测。

## 数据库与发布

- 不直接修改基线 `schema.sql` 来表示增量变更；所有结构调整使用编号迁移并补充迁移测试。
- 新配置先加入 `.env.docker.example`，只提交占位值；生产密钥通过部署机的密钥文件注入。
- 发布前执行 `docs/RELEASE-CHECKLIST.md`，保留当前版本和可回滚版本，完成健康检查、备份校验和回滚验证后再切换流量。

## 评审重点

优先检查数据丢失、越权、认证失效、上传安全、错误状态、移动端溢出、接口契约漂移、性能回退和缺失测试。发现问题时先列风险和复现步骤，再讨论代码风格。
